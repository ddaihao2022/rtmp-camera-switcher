## 一、总体结论

**系统能跑，核心业务链路是完整的；但当前状态适合演练和有人盯着的校内赛事，不适合“无人值守的正式赛事”。**

最需要警惕的不是程序崩溃，而是**“看起来操作成功了，其实没保存”**：

1. 选手照片、水印图片、整份配置稍大就触发 **413**，而前端多数请求不检查失败，界面没有任何提示；
2. 本地媒体“删除”接口实际是空操作，删完下一次刷新又回来；
3. 节目单在最后一节按“下一项”会**绕回第 1 节并清零跑表**；
4. 设置弹窗打开时，`PageDown`、`Enter`、`T` 等全局快捷键仍然生效，会在背后切节目、切 PGM、清零跑表；
5. 长时录制把两路视频全攒在渲染进程内存里，1 小时 1080p 双路约 3–4 GB，容易 OOM；保存时同步写盘会卡住整个服务端；
6. 单屏视图下，如果“输出”不是当前“预览”，录制会直接报“未找到输出视频元素”，但 PROGRAM 浮窗里明明在播。

**现场可用度：约 62 / 100。** 修掉下面 6 个 P0 后，常规校园赛事在有人值守的前提下可以做到稳定使用。

- 音频适配：AAC / MP3 直出；H.264 + Opus（enhanced FLV）视频直接 copy、音频转 AAC，不再出现「有画面没声音」。

## 四、P0 · 建议下次现场前必须处理

### P0-1 照片/水印/大配置触发 413，而且前端静默失败

**位置**
- `server/index.js:276`：`app.use(express.json())`，默认上限 100 kB
- `client/src/components/ScoreboardPanel.jsx:80-94`：`post()` 不检查 `r.ok`
- `client/src/components/ScoreboardPanel.jsx:131-139`：照片上传走同一个 `post()`
- `client/src/components/SettingsModal.jsx:44-66`：水印图片按原始文件转 base64 后整份 POST
- `client/src/components/ProgramSection.jsx:40-54`：节目单生成同样不检查 `r.ok`
- `client/src/App.jsx:339-353`：`bumpScore()` 先拉整份配置，再整份 POST 回去
- `client/src/utils/image.js:6`：照片压到 640 px / JPEG 0.82

**现象**
- 实测 150 kB 请求体直接 413，60 kB 正常。
- 640 px、质量 0.82 的实景照片转 base64 后常见 80–200 kB，**单张就可能超限**。
- `bumpScore()` 会把包含 `program` 和所有照片的整份配置回传；名册里只要有照片，导播台按一次“主+ / 客+”就可能 413，比分不变，界面也不报错。
- 水印图片没有压缩，手机拍的照片几乎必然超 100 kB。
- `post()` 里 `await r.json()` 遇到 Express 的 HTML 错误页会直接抛异常；`patchAthlete`、`save` 的调用方大多没有 `catch`，最后只表现为“点了一下，没反应”。
- 更隐蔽的是：`patchAthlete` 会先乐观更新本地 `cfg`，照片在界面上“已经出现”，但服务端没保存；刷新或另一块屏上就没了。
- 如果服务端返回的是 JSON 错误（400/500），`setCfg(prev => ({ ...DEFAULT, ...d }))` 还可能把错误对象当成配置写进界面，导致字段丢失。

**现场影响**
- 名册照片、改分、改道次数、生成节目单、水印图片，都可能在真实数据量下失效。
- 操作员看不到失败原因，只会重复点击或以为已经生效。

**建议**
- 把 `express.json()` 改成 `express.json({ limit: '8mb' })`，或只给 `/api/scoreboard`、`/api/watermark` 单独放宽。
- 所有前端 `fetch` 统一检查 `r.ok`，失败时弹出明确提示（例如“照片太大，未保存”）。
- `bumpScore` 只提交 `{ homeScore }` / `{ awayScore }` 增量，不要回传全量配置。
- 照片压到 360 px / 0.75，通常可控制在 30–60 kB；长期方案是照片落盘、配置只存 URL。
- 水印图片也走压缩，或改成独立上传接口。

### P0-2 本地媒体“删除”是空操作，删完还会回来

**位置**
- `server/index.js:851-856`
- `client/src/components/LocalMediaPanel.jsx:127-131`、`176-181`
- `client/src/App.jsx:549`
- `client/src/components/MediaLayer.jsx:100-123`

**现象**

```js
app.delete('/api/local/:key(*)', (req, res) => {
  const key = req.params.key;
  localFiles.delete(key);   // map 的 key 是 local/xxx，这里只有 xxx
  ...
  res.json({ success: true });
});
```

- 客户端传的是去掉 `local/` 前缀的 `xxx`，服务端 map 里存的是 `local/xxx`，所以永远删不到。
- 客户端 `handleRemove` 删完立即 `onRemove` 把本地列表过滤掉，看起来“删掉了”；下一次任意 `streamUpdate` 又把服务端条目推回来。
- 如果删的是当前输出，`selectedStream` / `outputStream` 不会清空；`MediaLayer` 找不到本地条目后会退化成 FLV 地址 `/local/xxx.flv`，输出画面变黑或报错。
- 删除按钮没有二次确认，也没有失败提示。

**现场影响**
- 赛前清理旧素材时“删了还在”，容易误以为已经清干净。
- 误删正在上屏的素材，PGM/HDMI 直接黑屏。

**建议**
- 与 PATCH 一致，先补 `local/` 前缀；删除成功返回 200，不存在返回 404，不要无条件 `success:true`。
- 删除后如果 `selectedOutputStream === key`，服务端清空并广播；客户端同步清空 `selectedStream`。
- 删除前加确认，尤其是正在输出的素材。

### P0-3 节目单末节循环 + 删除当前节会导致名册错位、跑表清零

**位置**
- `server/index.js:1309-1312`：`next` / `prev` 使用取模
- `server/index.js:1183-1213`：`applyProgramEntry()` 会重置跑表并清空名次/成绩
- `server/index.js:1204-1209`：新一节名册的 `place` / `result` 被清空
- `client/src/components/ProgramSection.jsx:69-72`：删除当前节时 `applyFirst:false`
- `client/src/components/TrackPanel.jsx:177-182`：侧栏“下一项 / 上一项”没有边界禁用
- `client/src/App.jsx:311-323`：`PageDown` / `PageUp` 全局可用

**现象**
- 在最后一节按“下一项”（或 `PageDown`），`(cur + 1) % length` 会绕回第 1 节；`applyProgramEntry` 同时把跑表清零、当前名次/成绩清空。操作员如果没盯着节目单，会以为还在最后一项，实际已经跳到第一项。
- 在第一节按“上一项”同理，会绕到最后一节。
- 删除当前节时，`remove()` 发送新节目单并带 `applyFirst:false`。服务端只更新 `programIndex`，**不重新应用当前节**；界面上的项目名和名册仍是刚删掉的那一节。下一次按“下一项”时，`snapshotProgramEntry` 会把这份“过期名册”写进新的当前节，**覆盖掉原本属于那一节的名册**。
- 删除节目单节、清空节目单、重新生成节目单都没有二次确认。

**现场影响**
- 误按 `PageDown` 可能直接换错项目、清零跑表、清空大屏成绩。
- 删除节目单节后继续操作，会静默破坏下一节的名册，属于数据丢失。

**建议**
- `next` / `prev` 到边界就停住，不要取模；侧栏在首/尾时禁用对应按钮，并显示“已是最后一项”。
- 删除当前节后，立即重新应用新的当前节（或清空当前名册并提示“请选择下一节”），不要让界面停留在已删除的数据上。
- 删除/清空/重新生成前加确认；清空节目单最好要求输入项目名或二次点击。
- 给 `programIndex` 增加一个“当前已应用节”的校验，切换前确认 `from` 指向的仍是同一节。

### P0-4 设置弹窗打开时全局快捷键仍生效；Shift+数字直切输出基本失效

**位置**
- `client/src/App.jsx:233-265`：数字键 / Shift+数字
- `client/src/App.jsx:268-300`：`Enter` / `Space` / `T` / `[` `]` / `I`
- `client/src/App.jsx:311-323`：`PageDown` / `PageUp`
- `client/src/App.jsx:29`：`settingsOpen` 状态没有被快捷键逻辑使用
- `client/src/components/SettingsModal.jsx:386-401`：设置弹窗结构
- `README.md:164-178`：快捷键说明

**现象**
- 快捷键只判断了 `INPUT` / `TEXTAREA` / `SELECT`，没有判断设置弹窗是否打开，也没有判断当前焦点是不是按钮。
- 在设置弹窗里按 `PageDown` 想往下翻，实际会**切换节目单到下一节并清零跑表**，同时 `preventDefault` 让页面不滚动。
- 在弹窗里焦点在“关闭”“保存”等按钮上按 `Enter` / `Space`，会触发导播台 CUT，而不是按钮本身。
- `T` 在弹窗空白处按一下就会开始/暂停跑表；`Shift+T` 会清零。
- `Shift+1`–`9` 的实现是 `parseInt(e.key, 10)`。标准 US/中文键盘布局下，按住 Shift 时 `e.key` 是 `!`、`@`、`#` 等符号，`parseInt` 得到 `NaN`，这个分支基本不会触发。README 里承诺的“Shift+数字直切 PGM”在现场很可能按不出来。
- README 只写了“输入框获焦时快捷键失效”，没有覆盖弹窗和按钮。

**现场影响**
- 这是最容易造成“误切 PGM、误清零跑表、误换节目”的一组问题，而且操作员往往意识不到是快捷键干的。

**建议**
- 所有全局快捷键开头加：`if (settingsOpen) return;`，以及 `if (e.target.closest('[role="dialog"]')) return;`。
- 只在 `document.activeElement === document.body`（或没有可交互元素获焦）时处理导播快捷键；按钮/链接获焦时不要抢 `Enter` / `Space`。
- 数字键改用 `e.code`（`Digit1`–`Digit9`）判断，Shift 分支就不会受符号影响。
- `PageDown` / `PageUp` 在弹窗、输入框、按钮获焦时都应失效。
- 跑表清零建议加二次确认或至少一个“撤销”提示。

### P0-5 长时录制全内存 + 同步写盘，1 小时双路可能 OOM / 卡死

**位置**
- `client/src/components/RecordPanel.jsx:256-259`：所有 `dataavailable` 分片都 `push` 进数组
- `client/src/components/RecordPanel.jsx:266`：每 500 ms 收一次数据，但从不落盘
- `client/src/components/RecordPanel.jsx:295-313`：停止时 `Blob` → `arrayBuffer` → IPC，至少两份完整副本
- `electron/main.js:506`、`534`：`fs.writeFileSync`
- `electron/main.js:82`：打包版服务端与 Electron 主进程同进程
- `client/src/components/RecordPanel.jsx:355-410`：界面只有已录时长，没有体积/上限提示

**现象**
- 两路 `MediaRecorder` 的所有分片都留在渲染进程内存里，停止时才组装。
- 1080p VP9 按 3–5 Mbps 估算，1 小时约 1.4–2.2 GB/路，双路 3–4 GB；再加上 `Blob` 和 `ArrayBuffer` 副本，Electron 渲染进程大概率 OOM。
- 保存时 `writeFileSync` 同步写几百 MB，会阻塞主进程；因为服务端也在这个进程里，RTMP 收流、HTTP-FLV、计时接口都会一起卡住。
- 界面没有“已录 30 分钟 / 约 2 GB”的提醒，也没有自动分段。

**现场影响**
- 长时间比赛/开幕式录到一半崩溃，文件直接没有。
- 保存瞬间全场推流抖动，甚至被判为掉线。

**建议**
- 用 `dataavailable` 分片经 IPC 流式追加到磁盘（主进程 `createWriteStream`），不要攒在内存。
- 至少加录制时长/体积上限，超过时自动分段并提示。
- 保存改成异步 `fs.promises.writeFile` 或写流，避免阻塞主进程。
- 录制中关闭窗口/刷新前给明确警告。

### P0-6 单屏视图下“输出 ≠ 预览”时，录制直接报找不到输出元素

**位置**
- `client/src/components/RecordPanel.jsx:209-213`：录制要求 `videoRefsMap.get(outputStream)`
- `client/src/App.jsx:43-56`：只有 `handleVideoReady` 注册过的元素才在 map 里
- `client/src/App.jsx:804-815`：单屏视图只渲染 `selectedStream`
- `client/src/App.jsx:412-426`：`handleSelectOutput` 只改 `outputStream`，不改 `selectedStream`
- `client/src/components/OutputMonitor.jsx:143-150`：PROGRAM 浮窗的 `<video>` 没有注册到 `videoRefsMap`

**现象**
- 单屏视图下只挂载当前预览的那一路。操作员用侧栏把另一路选为输出后，`outputStream` 是 camera 2，`selectedStream` 还是 camera 1。

**现场影响**

**建议**
- 录制不要依赖“碰巧被渲染”的预览元素。给 PGM 单独准备一个隐藏的 `<video>`（或让 `OutputMonitor` 注册它的元素），录制始终从这个专用元素取画面。

- 错误提示改成“输出画面尚未挂载，请切到导播台/网格视图或重新选择输出”。

### P1-1 图片顺序播放永远不触发；PGM/HDMI 也没有接顺序播放

**位置**

### P1-4 名册/项目名逐字 POST，广播可能把刚输入的字打回去

**位置**
- `client/src/components/ScoreboardPanel.jsx:80-99`：每次按键 `save()` → `post()`
- `client/src/components/ScoreboardPanel.jsx:121-127`、`330-376`：姓名/单位/号码/PB/亮点都是逐字保存
- `server/index.js:1069-1080`：每次变更全量 `io.emit('scoreboard:update')` + `persistScoreboard()`
- `server/index.js:424-439`：同步 `writeFileSync`

**现象**
- 每敲一个字就发一次请求、广播一次全量配置、同步写一次盘；配置里带照片时，单次广播可达数百 kB 到数 MB。
- `ScoreboardPanel` 同时监听 `scoreboard:update` 并 `setCfg(d)`；如果广播/响应比本地乐观更新晚到，输入框会被旧值覆盖，出现“打着打着少一个字/光标跳走”。
- `saving` 只是一个布尔值，并发请求时第一个响应就会把“保存中”关掉，指示不准确。
- 失败时没有 toast，只有右上角一个小圆点消失。

**建议**
- 文本输入改成本地草稿 + 300–500 ms 防抖保存；输入框获焦期间忽略同一字段的 socket 回包。
- `persistScoreboard` 改 300–500 ms 防抖 + 异步写。
- 保存状态改成“每个请求一个序号/计数”，不要用单个布尔值。
- 失败时明确提示“名册未保存”，并保留本地草稿。
